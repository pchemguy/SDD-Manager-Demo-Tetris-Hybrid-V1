# Available workflows

Select by the user's objective, not by which documents happen to be missing. A scoped request may enter any stage whose required inputs are established. A combined request may authorize preparation and implementation together; retain its explicit implementation boundary. Do not require fresh approval for a transition already covered by that request.

## Workflow selection and continuity

Apply at a development/functionality/review/revision request when no sufficient workflow context exists, and when a later request may change the active objective, scope or stopping boundary. The human need not name a skill or core workflow.

1. **Recover context.** At initial/reconstructed composite entry, apply [continuity](continuity.md) for branch discovery/selection and recovery from HANDOFF plus later records/Git; reuse an explicit or established branch choice. Use the request and established decisions; obtain `sdd-orient` evidence only where current project state is missing or stale. Distinguish a new project from existing or interrupted work, and recover the active workflow, stage, accepted inputs, pending human decisions, task range and unfinished owned work. Greenfield/brownfield is starting context, not a compulsory workflow choice.
2. **Select the path.** Apply the core definitions below. Whole-project definition/delivery uses main development; a bounded capability addition uses feature; review/correction/improvement uses revision. A human-directed amendment at a paused implementation checkpoint uses revision's steering variant. Preserve a narrow standalone operation or direct owner request when a full workflow is unnecessary. Treat explicit user selection as controlling within supported scope; ask only for a consequential ambiguity that prevents a sound selection.
3. **Assess continuity.** Determine whether the request continues the workflow, changes its stage/range, or switches workflows. A correction during preparation can remain with its current owner; a bounded addition does not require restarting main development. Do not switch from filenames, branch prefixes or missing documents alone. Before a switch, preserve pending work, authority and human checkpoints; apply the relevant branch/revision-mode procedure, including parent suspension/return where applicable. A switch cannot accept pending documents, widen scope or resume paused implementation.
4. **Load, report and route.** Load the selected workflow or operation instructions and relevant dependencies before stating its definitive procedure/checkpoints or beginning dependent work. Preserve a provisional selection as such while resolving instruction availability. Before dependent authoring/execution, give a concise user-visible chat brief: workflow/variant (or standalone operation), continuation/stage-change/switch decision and its request/project evidence, current stage and owner, authorized outputs and next human checkpoint/stop. Cite relevant paths or observed state; distinguish facts from uncertainty. At composite-workflow entry, material switching or context reconstruction, apply [bootstrap reporting](coordination.md#composite-workflow-bootstrap-reporting): announce Explicit, briefly explain profiles and state the subsequent level before dependent work. Visible progress commentary may carry the brief; hidden reasoning does not. Use only the selected owners and needed references, then act within the established boundary without another routine approval question.

Reuse an applicable selection and sufficient evidence on routine continuation; repeat the brief when the routing decision or authorized boundary materially changes. Use [scope checks and reporting detail](coordination.md#scope-checks-and-reporting-detail) for operational checks and adaptable event-based reporting; no per-response preamble, new journal or mandatory selection file is required.

## Core development workflows

Choose among three core workflows by the intended change. They describe purpose and overall path; focused skills and the operation catalog below supply reusable stages. A workflow name grants no authorization or branch destination. Apply **sdd-conventions**' **Workflow identity** and [branch management](branch-management.md) for actual names and target context.

| Workflow | Purpose | Typical path |
| --- | --- | --- |
| Main development | Define and deliver the complete intended project, reusing sufficient accepted inputs when available. | Exploration → PROJECT → ARCHITECTURE → DECOMPOSITION → SPEC → PLAN/layout → TASKS → bounded implementation and verification. |
| Revision | Correct, simplify, or improve previously defined or implemented work. | Review plan when needed → review → review report → revision plan → revision → revision report. |
| Feature | Add a scoped capability to an existing system. | Necessary feature design/specification/plan documents → FEATURE-TASKS → implementation → accepted document incorporation and verification. |

- **Entry:** Main development covers both new and existing projects: greenfield starts from exploration; an existing project may enter at an established stage. Reuse accepted inputs rather than replaying stages.
- **Scope selection:** Main development addresses whole-project definition and delivery. Feature is the usual route for a bounded addition to an existing project; an existing project needing whole-system specification/planning can use main development. Revision addresses corrections to defined or implemented work. Greenfield/brownfield describes starting context, not a separate workflow or compulsory routing rule.
- **Revision scope:** Use [review and revision](review-and-revision.md) for formal campaigns. Use [revision modes](revision-modes.md) for a nested revision’s suspended parent/default return target or a human-authorized eligible reopened campaign amendment. A focused prompt may define review scope or an accepted revision directly; do not invent a preceding review or mandatory artifact stage when it adds no needed evidence.
- **Feature preparation:** Define the scoped feature package on a dedicated design-docs branch before dependent implementation, using only the design, specification, and planning deltas it needs. Explicitly merge accepted project preparation into the default branch before creating the feature implementation branch. FEATURE-TASKS governs active task-list feature work. Reuse sufficient existing design/layout; not every correction needs a feature package.
- **Shared execution:** Implement only the authorized bounded scope. Apply relevant verification and commit/push checkpoints under [Git workflows](git-workflows.md). Main development uses phase branches: partial ranges pause after pushes, complete phases explicitly integrate, and an authorized next phase starts from updated main. Revision/feature and steering use their applicable integration gates. Preparation, assessment, and review stop before implementation unless it is authorized. A narrow task request does not authorize unrelated incorporation or a whole-project campaign.

### Steering as lightweight revision

**sdd-steer** is the focused human-directed revision path at a paused task-list checkpoint, especially for reducing implemented functionality. The human supplies the amendment objective and commands execution. Steering directly updates affected existing documents, code, tests, and documentation; it creates no feature-document layer and requires no feature-document integration step or obligatory formal review/revision campaign.

Steering still verifies, commits/pushes, explicitly integrates into the paused implementation branch, verifies/publishes that target, and reports. It returns control without handing off to or resuming sdd-implement; the human separately resumes the task list. A broader revision may use the formal campaign instead. Steering is a revision variant, not a fourth core workflow.

## Workflow loading

Use this operation when the human asks to read, load or explain SDD Manager workflows before development. It is distinct from preparing project documents. Greenfield selects the new-project starting context of main development, not a separate core workflow.

1. Identify the requested workflow or operation and the purpose of this loading turn. Use supplied context; recover target-project evidence only when the request needs it. A generic workflow explanation requires no target repository or Git worktree.
2. Read the coordinator entry and selected workflow/operation instructions, including dependencies governing relevant transitions and human checkpoints. Load selectively; do not read unrelated workflows or every reference. If a required source is unavailable, identify that limit rather than claim it was loaded or the procedure is established.
3. Report in chat the repository paths of sources actually read, applicable stage sequence and human checkpoints, authorized work/outputs and exclusions, and the next step. Distinguish the documented path from actual project readiness or approvals. Honor an explicit request for sources even when routine reporting detail is reduced.
4. Stop at the requested loading boundary. Do not create project files, bootstrap records, branches, hosted objects or commits merely to prepare the workflow. Loading instructions neither accepts artifacts nor authorizes subsequent development.

## Release operations

For requested release publication, apply the [advisory prerelease review reminder](prerelease-review.md#advisory-release-reminder) at entry and carry its disposition through the release handoff. The shared policy defines when to remind and how to continue; selecting release work does not select review.

| Request | Route and boundary |
| --- | --- |
| Prepare/draft/assemble/update a release message or release notes | Coordinate [complete message preparation](../../sdd-forge/references/release-message.md): forge supplies validated Git highlights, report assembles applicable ancillary sections, and manage establishes output ownership. Retain body-only root `RELEASE-NOTES.md`, refreshing/replacing it atomically on subsequent preparation. No provider, tracking, release/tag writes or dispatch is required. Explicit supplied-text-only editing keeps its narrower scope. |
| Collect/revise highlights since a release | Use sdd-forge’s [shared Git highlights](../../sdd-forge/references/release-highlights.md) before provider selection and sdd-report for curation. Coordinate draft/ignore ownership and exact source coverage. Return the ignored local draft or finalized body; no hosting access, TASKS, release/tag creation or publication is required. |
| Assess a package or develop release packaging/workflow | Use sdd-forge's [package preparation](../../sdd-forge/references/github-packaging.md) and [release workflow](../../sdd-forge/references/github-release-workflows.md) guidance. Coordinate accepted repository edits, meaningful checks, commits/pushes and eligible integration through existing Git ownership. Retain interactive decisions; stop before product release publication unless requested. |
| Create/finish a release or run its established workflow | Pass repository, exact verified source/tag, package set, notes, state/latest policy and authorized effects to sdd-forge's [release lifecycle](../../sdd-forge/references/github-releases.md). Verify/refresh retained complete notes using local provenance and version agreement; coordinate the release commit whose body is the complete message and the tag on that exact verified commit. Create/update shared highlights through the exact source before the new tag becomes a baseline, establish finalized-notes transfer, select one publisher, coordinate any necessary tag/Git work, verify actual outputs and remote state, verify the published complete body before cleaning up only the owned internal highlights checkpoint; retain the complete-message file, then return release URLs/evidence or pending effects. |

Release requests do not require TASKS, GitHub tracking activation or automatic phase-end release creation. Existing source/build documentation supplies sufficient contracts for a scoped package request; consequential unresolved choices return to the user, while routine authorized steps proceed. Use sdd-verify's [release checks](../../sdd-verify/references/release-checks.md) and sdd-report's [release reporting](../../sdd-report/references/releases.md). Permission recovery distinguishes workflow-file modification, release writes and workflow dispatch.

## Delivery strategy handoff

Commit preimplementation project artifacts and adjacent QC reports on the designated design-docs branch. Completed main preparation, including preparation-only, follows [its completion sequence](main-preparation.md#final-package-qc-integration-and-checkpoint): verified/published documentation integration, enabled docs-main milestone closure and the final preimplementation checkpoint. Other preparation-only paths stop on design-docs. Honor explicit earlier, no-merge and local-only limits. Before an authorized implementation handoff, complete [preparation integration](branch-management.md#preparation-integration-gate), then branch from the recorded integration parent containing that published checkpoint; the implementation range still needs authorization. Campaign review/revision records remain on their revision branch and do not require this project-document stage.

Preparation carries the accepted design/contracts into an early meaningful end-to-end MVP and small testable capability increments through **sdd-plan**, then derives their bounded executable work through **sdd-tasks**. Retain complete intended design and SPEC, justified prerequisite exceptions, preserved useful behavior, and relevant exit evidence. A scoped feature uses the earliest meaningful changed path rather than rebuilding the whole project.

Pass the selected range, owning capability/milestone outcomes, dependencies, verification obligations, and applicable human decision gates into implementation. At consequential checkpoints, return the demonstrated functionality and relevant usability/risk evidence for the human's continue/amend/simplify/stop decision. This does not authorize automatic steering, broaden the selected range, or require approval for routine work already authorized.

## Feature sequencing

- **Preparation:** Establish the convention's campaign/package identity and `design-docs/<campaign>-<slug>` under [branch management](branch-management.md). Create its features-directory README linking active root FEATURE sources and both branch stages; preserve another active package in the same worktree. Establish the entry HANDOFF with scope, parent and active package links under [continuity](continuity.md); intermediate approvals stay in their existing evidence, with refresh at completed preparation/integration. Keep feature deltas distinguishable from complete main documents. Creating a feature task list does not require immediate incorporation into TASKS.
- **Implementation:** Explicitly merge, verify and publish the accepted feature preparation into the default branch before creating `feature/<campaign>-<slug>` from its recorded integration parent containing that checkpoint. If that parent is an active phase, apply the preparation gate's verified propagation step first; final integration returns to the creation parent. Accepted FEATURE-TASKS can then drive implementation while its authoritative feature documents remain active. Identify those sources explicitly in the handoff.
- **Document integration:** Incorporate accepted targets included in the request on the feature branch before final verification and Git merge. A complete feature implementation includes incorporation needed for a coherent final project; a preparation-only or narrow task request does not authorize unrelated incorporation. Do not infer acceptance from passing tests.
- **Archive:** After accepted final incorporation and task/evidence disposition, **sdd-integrate-feature** retains eligible sources under the package directory, repairs selected links, and marks historical snapshots. Partial/narrow integration retains needed active documents; verify archive ownership before final merge.
- **Git integration:** Merge the verified completed implementation boundary into its established target by default with an explicit merge commit, verify the merged state, and publish the target. Preparation-only persists its documents on design-docs and stops before implementation. The earlier preparation merge is a separate document-only boundary.
- **Consistency:** If the selected work requires an unresolved contract or dependency decision, report it before the dependent mutation. Continue independent authorized work when sound.

## Cross-cutting operations

- **Reporting:** Use **sdd-report** throughout, or independently for an issue, commit message, PR description, or progress report. Drafting PR text does not create or merge a PR.
- **Hosted tracking:** Local workflows remain usable when tracking is not selected; selection makes its gates required for dependent execution. Hosting outages permit independent execution only in an already verified activated phase for projected tasks with satisfied dependencies; preserve verified local results and report pending closure without waiving initial/added-work or transition gates. Apply the shared backend lifecycle: activate/project only an eligible phase before its first task; coordinate committed milestone/phase review tasks and reports, task issue closure and then milestone closure; gate next-phase activation on verified predecessor integration/publication. Use phase activation for the transition. When tracking is active, coordinate task associations before commit composition and verified closure through **sdd-forge**; issue state never supplies completion evidence.
- **Authentication:** Attempt authorized pushes using existing shell authentication. Route access/credential failures to the coordinator's repository-token recovery protocol; preserve distinct Git and API access and the active backend's permission profile.
- **Continuity:** All composite workflows and focused calls affecting them use [checkpoint/recovery](continuity.md). Supporting and release operations return material state/decision changes to the active owner; do not invent task campaigns or change release-message, commit/tag or provider rules to maintain a handoff.
- **Persistence:** Implementation and steering own their commits and pushes. Coordinate persistence of other authorized repository edits through the shared protocol; hosted-only changes have no local commit by implication.

## Optional tracking decision at handoff

Use **sdd-manage**'s [tracking decision](tracking-decision.md) before dependent phase activation. Carry the recommendation, actual confirmation/decline, repository/scope and observed hosted state separately. A supplied GitHub token recommends enabled tracking but does not activate it; unresolved activation choices return to the manager. Reuse confirmed scope without repeated approval. Late confirmation reconciles retained evidence instead of replaying product tasks.

## Human preparation sequence

Use [human document review](human-document-review.md) for both initial and feature preparation. Guide the human through every necessary newly created root/proposal; hold dependent progression for its acceptance. PROJECT, ARCHITECTURE, DECOMPOSITION, SPEC, PLAN, layout and TASKS each have their own boundary; PLAN/layout are separate even in a combined request. Feature campaigns review their necessary deltas and reuse sufficient existing main inputs without inventing optional overlays.

At startup or after interruption, assess existing progress and continue from the next eligible stage by default. An explicitly requested interactive review comes first; important issues can prompt a concern and offer. Preserve actual pending human boundaries. Agent QC and broad continuation authority do not replace the creation checkpoints.
